# 边缘模式后台刷新尺寸修复设计

## 问题与根因

完整模式进入边缘窥视后，额度或积分账户在后台刷新时会调用 `syncMainWindowHeight()`。该函数只排除了极简模式和设置页，没有识别边缘会话，因此会读取边缘条当前的 20 或 135 像素内容宽度，并调用 `set_main_window_size`。原生端随后用这个错误宽度调整主窗口，导致边缘条或再次展开的完整窗口偶发出现异常尺寸。

确定性诊断回路连续三次复现：完整模式收起后触发一次积分显示变化，每次都会产生 3 个不应出现的 `set_main_window_size` 调用。

## 修复行为

- 额度和积分数据继续在后台正常刷新，不因边缘状态暂停网络请求或数据渲染。
- 边缘进度条继续使用最新的 Codex 5 小时剩余额度。
- 完整或极简模式处于边缘会话时，包括收起、悬停展开和过渡阶段，内容变化不得调用 `set_main_window_size`。
- 后台刷新不得为了展示数据而展开完整窗口，也不得改变边缘条尺寸。
- 悬停边缘条时仍按进入边缘前保存的来源模式和窗口尺寸展开，并直接显示已刷新的数据。
- 用户拖出边缘状态后，后续正常内容变化恢复完整窗口高度同步。

## 实现范围

在前端 `syncMainWindowHeight()` 的入口增加边缘状态保护。只要存在边缘方向或正在执行边缘收起／展开过渡，就直接跳过原生尺寸请求。

不修改 Rust 的边缘尺寸保存、DPI 换算、定位或展开接口。现有路径已在 1.5 倍缩放及自定义完整窗口尺寸测试中正确恢复物理尺寸，修改它们会扩大风险且不能解决已复现的错误调用。

## 回归验证

- 将诊断回路固化到 `scripts/test-refresh-lifecycle.mjs`，记录 `set_main_window_size` 调用。
- 验证完整模式边缘条收起后，积分显隐变化不会发出尺寸请求。
- 验证完整模式从边缘条悬停展开后，后台数据变化仍不会覆盖保存的展开尺寸。
- 验证退出边缘状态后，普通完整模式仍会按内容变化同步高度。
- 保留完整与极简来源模式、启动不误吸附、悬停、离开及拖动重新吸附的现有回归测试。
- 运行前端生命周期测试、Rust 测试、完整构建、版本一致性检查和 `git diff --check`。
